# AGENTS.md

## Layout

- Single Maven module: `demo/`. The repo root has **no** build file — all Maven commands run from `demo/`.
- Repo root is **not** a git repository. Do not assume branches, commits, or CI exist; there is no CI, no lint/format config, and no pre-commit hooks. Don't invent them.
- Root also holds `.vscode/` (JDT LS heap config only) and `.github/modernize/java-upgrade/` (VS Code Java-upgrade tool hook scripts, unrelated to the build).
- `demo/project-Info.md` is the original user requirement list. It is loosely worded and has been implemented; read it for intent, not for exact strings.
- `demo/HELP.md` is auto-generated by the Spring Initializr and is listed in `.gitignore`. Ignore it; it is not documentation.

## Commands (Windows PowerShell, from `demo/`)

Use the wrapper, not a system `mvn`: `.\mvnw.cmd` (plain `mvnw` will not resolve without `.\`).
The wrapper is script-only (`distributionType=only-script`, no `maven-wrapper.jar`), so it bootstraps Maven 3.9.16 itself — no local Maven install needed.

```powershell
.\mvnw.cmd test                   # the only verification gate (~30s; context boot dominates)
.\mvnw.cmd -o test                # -o works offline; all deps are already in ~/.m2
.\mvnw.cmd spring-boot:run        # http://localhost:8080
.\mvnw.cmd package -DskipTests    # target\demo-0.0.1-SNAPSHOT.jar, for a `java -jar` manual run
.\mvnw.cmd clean                  # needed after test/package if target\*.jar is locked
```

There is no separate lint or typecheck step — `test` is the only gate.

## Spring Boot 4.1.1 (this is NOT Boot 3)

`demo/pom.xml` pins Boot **4.1.1** with Java **21**. The Boot 4 dependency layout differs from Boot 2/3 — do not "fix" the pom toward older conventions:

- Web starter is `spring-boot-starter-webmvc`. There is no `spring-boot-starter-web`.
- The pom uses **per-starter test artifacts** (`spring-boot-starter-webmvc-test`, `-data-jpa-test`, `-security-test`, `-thymeleaf-test`, `-validation-test`, `-actuator-test`) rather than the aggregate. `spring-boot-starter-test` 4.1.1 does still exist, so either works — but match the existing pom and add the `-test` artifact for whatever you use.
- **Test annotations moved packages** in Boot 4: `@DataJpaTest` is `org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest`; `@WebMvcTest` / `@AutoConfigureMockMvc` are `org.springframework.boot.webmvc.test.autoconfigure.*`. The old `org.springframework.boot.test.autoconfigure.*` packages are gone.
- Spring Security is **7.1.1**. `WebSecurityConfigurerAdapter` is long gone; use `SecurityFilterChain` beans. `thymeleaf-extras-springsecurity6` (3.1.5) is on the classpath but **unused** — templates read model attributes instead of the `sec:` dialect, which keeps fragments renderable without a security context.
- Hibernate is 7.4.x → JPA/Security/Validation APIs are `jakarta.*`, not `javax.*`.
- Actuator, DevTools, and `spring-boot-h2console` are on the classpath already.

## UI stack

`demo/` ships three large, authoritative agent references. They **are** the frontend spec — read the relevant one before writing any markup or CSS, and do not duplicate their content here:

- `bootstrap-5.3-coding-agent-reference.md` — Bootstrap 5.3 is the UI foundation. Bootstrap 5.3 syntax only (`ms-*`/`me-*`, `data-bs-*`; never Bootstrap 4 `ml-*`/`data-toggle`).
- `htmx-project-reference.md` — server-rendered HTML fragments over JSON/REST-for-its-own-sake. §46/§44 define the Spring layout below.
- `css-project-reference.md` — custom CSS only for what Bootstrap utilities can't express.

Asset delivery: **CDN `<link>`/`<script>` tags in Thymeleaf templates** (bootstrap 5.3.8, htmx 2.0.11), with `integrity`/`crossorigin` in `fragments/layout.html`. No WebJars. Do not add a `webjars` dependency or a second CSS framework.

**The `integrity` hashes are version-specific and must be recomputed whenever a CDN version changes.** A stale hash does not degrade gracefully — the browser refuses the asset outright, so every Bootstrap behaviour (modal, dropdown, collapse, navbar toggle) and all of htmx go dead at once with no visible error in the markup. This was the root cause of "the Add New Note button does nothing". To re-derive them after a version bump:

```powershell
$wc = New-Object System.Net.WebClient
$bytes = $wc.DownloadData('<cdn url>')
'sha384-' + [BitConverter]::ToString([Security.Cryptography.SHA384]::Create().ComputeHash($bytes)).Replace('-','').ToLower()
```

## What the app is

A token-authenticated "Memory Notes" pad, built from `demo/project-Info.md`. Everything below exists and is verified end to end.

- **Pages** — `templates/pages/`: `home`, `about`, `notes`, `login`, `signup`, `error`. Each is a full document that pulls in `fragments/layout.html` (`head`, `navbar`, `footer`, `scripts`).
- **Fragments** — `templates/fragments/`: `notes-grid` (`grid(notes, oob)`), `note-card` (`card(note)`), `note-form` (`form`), `note-edit-form` (`form(note)`), `note-created` (`created(notes)`), `error-alert` (`alert(message)`), `flash` (`messages`).
- **Fragment files have no `<html>`/`<body>` wrapper.** Controllers return them directly as htmx partials, so a document wrapper would ship invalid markup inside a swap. Keep it that way.
- **Assets** — `static/css/app.css` (design tokens, the Bootstrap `--bs-*` bridge, and the named components Bootstrap utilities can't express) and `static/js/app.js` (CSRF header on every htmx request, 422-swap opt-in, modal close on the create marker, theme toggle, bio counter).
- **Design tokens** — `app.css` is the only place a colour, radius, shadow or spacing value is written. `:root` holds the light palette, `[data-bs-theme="dark"]` re-points the same token names, and a bridge block maps them onto `--bs-body-*` / `--bs-primary*` / `--bs-link-*` / `--bs-border-*`. Component rules are `mn-`-prefixed BEM. Two things not to undo: Bootstrap's own `--bs-btn-*` ramp has to be pointed at the tokens by hand (`.btn-primary` hard-codes it), and **do not use `@layer`** — Bootstrap is unlayered, so anything the app puts in a layer loses to it.
- **Theme** — Bootstrap 5.3's native `data-bs-theme` on `<html>`. A ~10-line inline script in `fragments/layout :: head` applies the stored choice *before first paint*; `app.js` only flips it on click and writes `localStorage["mn-theme"]`.
- **Notes grid model** — `NoteController.gridAttributes()` builds `notes` + `noteCounts` + `noteTotal` in one place, because the grid fragment is rendered from four routes (first paint, edit-cancel, create, delete). Returned as a `Map<String, Object>` and applied with `model.addAllAttributes` / `mav.addAllObjects`, since `Model` and `ModelAndView` share no supertype for attributes in this Spring version. `noteCounts` is keyed by `Category.name()` as a **String**: SpEL cannot index an `EnumMap` with a string key.
- **Auth** — random 32-byte token, SHA-256 digest + expiry on `AuthSource`, HttpOnly `note_token` cookie, `SessionCreationPolicy.STATELESS`. Signup issues a token immediately; login goes through the form-login filter and a success handler that issues one. Every request re-resolves the cookie in `TokenAuthenticationFilter`.
- **Visibility rules** — `/`, `/login`, `/signup`, `/error`, static assets and `/actuator/health` are public; `anyRequest().authenticated()` covers everything else, so `/about`, `/notes` and every `/fragments` partial need a token. `LoginRedirectEntryPoint` sends anonymous callers to `/login?returnUrl=<path>`. Edit/delete additionally require ownership (`Note.owner_id`). `/h2-console` is **open on purpose** — see "h2-console is unauthenticated" below.
- **Profile bio** — `AuthService.MIN_BIO_LENGTH = 150`. An empty bio is allowed; a non-empty one must be at least 150 trimmed characters. Enforced by `minlength` in the markup and by `validateBio` server side.
- **Progressive enhancement** — every htmx form is a working plain form. `NoteController` branches on the `HX-Request` header: htmx gets a fragment (422 + re-rendered form on validation failure), a browser gets a redirect.

## Deviations from `project-Info.md`, and why

These are deliberate. Don't "fix" them back without asking.

- **No `spring.security.user.*` in `application.properties`.** The file asks for hardcoded admin credentials. Signup writes to `AuthSource` and `AppUserDetailsService` authenticates against that table, so a fixed user entry would be inert at best and would mask real signup bugs at worst. `application.properties` carries a comment saying so.
- **`Note.owner_id` and `Note.updatedAt` were added** beyond the listed columns. Without an owner there is nothing to enforce edit/delete permissions against; `updatedAt` backs the "Issue fixed info" spirit of `ErrorEnquiry`.
- **`AuthSource.bio` was added** to back the profile dropdown the requirements ask for.
- **Column name is `password`**, not `password_hash` — matching the requirement's "password in encoding format". It holds a BCrypt digest, never plaintext.
- **h2-console is unauthenticated.** `project-Info.md` §"Database security" asked for `/h2-console` → `/login` → back to the console. The user reversed that: opening `/h2-console` should go straight to H2's own JDBC sign-in form. `H2ConsoleAuthFilter` was deleted for it. `SecurityConfig` permits `/h2-console/**` and calls `csrf.ignoringRequestMatchers("/h2-console/**")` — that second part is load-bearing, not tidiness. The console's sign-in is a plain form POST to `/h2-console/login.do?jsessionid=…` carrying no CSRF token, so leaving CSRF on returns **403** and the console becomes unusable. Treat this as a dev/operator tool: it exposes the full database (including `AuthSource` password digests) to anyone who can reach the port, so it must not be published anywhere real.

## Current state — verified gotchas

- **Tests: 53, all green** — `DemoApplicationTests`, `Model.CategoryTest`, `Security.ConsoleAccessTest`, `Security.CsrfTokenRepositoryTest`, `Security.LoginRedirectEntryPointTest`, `Security.PageRenderingTest`, `Security.TokenServiceTest`, `Service.AuthServiceTest`, `Service.NoteServiceTest`.
- **The CSRF token is never allowed to expire — this is load-bearing.** `TokenAuthenticationFilter` builds a *new* `Authentication` from the cookie on every request, so Spring Security's `CsrfAuthenticationStrategy` treats every single request as an identity change and rotates the token. Responses then go out with `XSRF-TOKEN=; Expires=1970`, which makes every mutation after the first 403 — and a reload doesn't help, because the re-render hands out a token the *next* mutation then consumes. `Security/PersistentCookieCsrfTokenRepository.java` fixes it by ignoring `saveToken(null, ...)`; `SecurityConfig` additionally drops `CsrfAuthenticationStrategy` through an explicit `sessionAuthenticationStrategy()`. Do not "clean up" either one. Rotating a token guards a *session*-bound identity; this app is stateless and the identity lives in an HttpOnly cookie, so rotation only breaks an open tab.
- **The CSRF header is `X-XSRF-TOKEN`, not `X-CSRF-TOKEN`.** A `CookieCsrfTokenRepository` names its own header, so `CsrfTokenRequestAttributeHandler` (unmasked, the cookie value) publishes that name in the `csrf-header` meta tag. `app.js` reads it from there instead of hardcoding it; anything else that posts by hand — a test, a curl, a new fragment — must do the same or it will 403. Same reason there is no response header to refresh from.
- **`NoteService.findAll()` is not owner-scoped**, so every signed-in user sees every note and `countByCategory()` totals the whole table. That is pre-existing and consistent with what the UI shows; the stat strip is not the bug. `Note.owner_id` is only enforced on edit/delete. Scoping the list to the authenticated owner is a deliberate future change, not a drive-by fix.
- **The test classes share one in-memory database.** `webEnvironment = RANDOM_PORT` reuses the cached Spring context, so H2 survives across classes and across methods inside a class. Assertions must not assume an absolute note count — see the regex in `PageRenderingTest` — and a counter used to build usernames has to be `static` or the second method gets a username the first already registered.
- **`Vary: HX-Request` has to be set on the response, not by an advice.** `@ControllerAdvice` handlers run before the controller method, so they cannot see the handler's `HttpServletResponse`; `VaryOnHtmqAdvice` was tried and deleted. `NoteController.markVaryOnHtmx(response)` appends to the existing `Vary` list (theme cookie and htmx can both need it) on every fragment route.
- **HTMX attributes need `th:attr`, not `th:hx-*`.** Thymeleaf only evaluates `@{...}` inside attributes its own dialect knows (`th:href`, `th:action`, `th:src`, …). `th:hx-post="@{/notes}"` strips the prefix and ships the *literal* string `hx-post="@{/notes}"`, so htmx requests a URL containing `@{`. Use `th:attr="hx-post=@{...}"`. Same for `hx-get` and `hx-delete`.
- **A CDN asset that fails its SRI check fails silently.** Nothing in the markup looks wrong, but the browser refuses to load the file, so Bootstrap's JS-driven behaviour (modal, dropdown, collapse) is simply absent. Symptom to recognise: "the button does nothing" with a correct-looking `data-bs-toggle="modal"`. Check the `integrity` hash before looking at the template.
- **MockMvc cannot test the H2 console.** The console is a servlet registration, not a `@RequestMapping`, so MockMvc 404s it into the app's error page. `Security.ConsoleAccessTest` uses `webEnvironment = RANDOM_PORT` with a JDK `HttpClient` instead. Two wrinkles if you extend it: H2 redirects `/h2-console` → `/h2-console/` and serves a JS-bounce page (assert on `<title>H2 Console</title>`, not on a login form), and the real sign-in needs the `jsessionid` from that page.
- **Stale app instances silently poison manual testing.** A leftover `java -jar target\...` **or the `memory-notes` container** keeps port 8080 and answers requests with an old image and an old in-memory DB, which looks exactly like a data bug and can make correct code look broken. Before a manual run: `Get-NetTCPConnection -LocalPort 8080 -State Listen`, then kill the owner — `wslrelay.exe`/`com.docker.backend.exe` there mean a container still owns the port, so use `docker compose down`. Always confirm the port owner is the PID you just started.
- **The VS Code JDT language server compiles into `target/` too.** If it has an unresolved error it leaves a class that throws `java.lang.Error: Unresolved compilation problem` at surefire, with a duplicate test class from the old package path. `.\mvnw.cmd clean` fixes it; a real fix is a matching `package` declaration and directory.
- **H2 is in-memory**, so all data is lost on restart. The URL is `${DATABASE_URL:jdbc:h2:mem:NoteDB;...}`; override it with a `jdbc:h2:file:` URL to persist (what the compose volume is mounted for).
- **`th:remove`/`th:replace` on wrappers in fragment files would break direct rendering** — see "Fragment files have no wrapper" above.
- `HelloController` (`GET /hello`) is leftover scaffold returning a plain string. It is unused by the app and harmless; delete it if you want the surface clean.
- DevTools is active: logs show thread `restartedMain` and the app restarts on classpath changes. Only 1 actuator endpoint (`health`) is exposed.
